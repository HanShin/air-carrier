# 자동 감사 전투 지점 → F9 재현실

기준일: 2026-09-05. 기존 `HeadlessPlaythrough`의 항로·사건·항구 구매·전투 명령을 그대로 실행하다가, 지정한 전투의 지정 틱에서 전체 상태를 불변 스냅샷으로 내보냅니다. 새 전투를 꾸미거나 시드를 다시 검색하지 않습니다. **자동 플레이 재개/명령 리플레이가 아니라 사람이 동일 상태를 비교하기 위한 시작점**입니다.

## 내보내기와 불러오기

Python 3와 Mono의 `csc`/`mono`가 필요합니다. Unity는 내보내기에는 필요 없으며, 불러오기에는 개발 빌드 또는 에디터를 사용합니다.

```sh
bash tools/run_headless_audit.sh 1 Standard 17000 \
  --flagship=ship_zephyr --wings=adaptive \
  --snapshot-dir=/tmp/aether-checkpoints \
  --snapshot-battle=21 --snapshot-tick=100
```

성공하면 `SNAPSHOT <전체 경로>`와 캡처 지점을 출력합니다. 파일 경로를 게임 **F9 → 스냅샷 경로 → 불러오기**에 입력하거나 다음처럼 실행합니다.

```sh
open -na Builds/AetherArk.app --args -debug-snapshot "/absolute/path/to/capture.json"
```

재현실에서 **감사 전투 번호·틱·편대 정책·수동 이어하기** 안내를 볼 수 있습니다. 불러온 사본은 멈춘 상태이며 **F8**로 0.1초씩 진행할 수 있습니다. 일반 프로필·원정은 기존 재현실과 동일하게 격리됩니다. 출력 폴더를 지정해도 그 안의 기존 캡처나 일반 세이브를 덮어쓰지 않습니다. F9의 **최근 캡처** 검색은 앱의 `reproduction/snapshots`만 확인하므로 `/tmp` 등 다른 폴더의 파일은 전체 경로로 지정합니다.

macOS 실행 검수에서는 Documents 안의 저장소 픽스처를 직접 열 때 파일 `open`에서 대기하여 창이 응답하지 않았습니다. 보호 폴더 접근 권한은 변경하지 않았으며, 이미 감사 도구가 `/tmp`에 내보낸 동일 캡처를 사용하자 정상 복원됐습니다. 위 예시처럼 검수용 출력 폴더를 사용하십시오. 이 현상을 스냅샷 손상이나 전투 교착으로 판단하지 않습니다.

## 지점의 정확한 의미

- `--snapshot-battle=N`: **캠페인 전체에서 1부터 세는 전투 순서**입니다. 지역 번호·노드 번호·적 티어가 아닙니다. 사건에서 발생한 전투와 지역 관문도 포함합니다.
- `--snapshot-tick=0`: 해당 전투 진입 직후이며, 감사의 초기 공명자 이동/무장 전력 배분 명령도 아직 수행하지 않았습니다. `--enemy=`를 사용했다면 강제 적 교체만 이미 적용되어 있습니다.
- `--snapshot-tick=N` (`N > 0`): 해당 전투의 `Tick(0.1f)`를 정확히 N번 마친 직후, 다음 감사 명령 묶음을 실행하기 전입니다. 다음 발사/출격/과부하/수리 지시를 미리 실행하지 않습니다. 내부 누적 float 시간은 `10.0000019`처럼 보일 수 있으므로 틱 번호가 기준입니다.
- 세 옵션은 함께 사용해야 합니다. 일반 캠페인은 **1회·난이도·정확한 signed 32-bit 시드**를 모두 지정합니다. 튜토리얼만 `--tutorial`로 생략 가능하며, 시드 32838만 지정하면 여전히 6공역 캠페인입니다.
- 틱 범위는 0..36001, 전투 번호는 1 이상입니다. 실제 도달 가능 여부는 전투 종료와 `--combat-cap`에 따릅니다. 기본 전투 제한 420초는 바꾸지 않았습니다.
- 캡처 성공은 종료 코드 **0**, 전투 종료·원정 종료·이전 전투 제한 등으로 지점에 도달하지 못하면 **4**입니다. 미도달 시 파일을 만들지 않으며 다른 전투/시드로 대체하지 않습니다. 제한 틱에서도 여전히 Combat이면 캡처할 수 있지만 승패 상태는 캡처하지 않습니다.
- 캡처는 완주 통계가 아니므로 `--records`/`--report`와 함께 사용할 수 없습니다. 일반 감사의 종료 코드 0/1/2/3과 출력은 유지했습니다.

## 보존되는 정보와 한계

기존 형식 `aether-ark-combat-snapshot` v1을 공유합니다. 전체 `RunState`·`ProfileState`에 선택적 `audit` 출처 정보를 더했으며 이전 Unity 캡처도 계속 불러올 수 있습니다. 일반 런/프로필 스키마는 v2 그대로입니다.

- 선체·설비·구획·경고·일시정지·전투 타이머·선원 이동 좌표/경로·편대/조종사 상태·장비·자원·항로와 route/combat/events RNG를 보존합니다.
- 출처에는 전투 순서, 완료 틱, 0.1초 간격, 캡처 경계, 편대 정책, 전략, 강제 적 여부, 전투 제한, **컴파일 시점 소스 SHA-256**이 들어갑니다. 시드·기함·난이도·튜토리얼 여부는 함께 저장한 원정/프로필에 있습니다.
- 어셈블리 MVID와 `headless-mono/<런타임 버전>`으로 생산 환경을 표시합니다. 감사 소스와 Unity 콘텐츠가 같은 체크아웃이어도 Mono 실행 파일은 Unity 빌드와 같다고 주장하지 않으며 항상 기존 빌드 차이 경고를 표시합니다.
- 공용 파일 게시 코드가 UTF-8·SHA-256·8MiB 제한·고유 파일명·같은 폴더 임시 파일/flush/이동을 처리합니다. 감사 직렬화는 상태 계약의 public 필드만 기록하고 float를 round-trip 정밀도로 출력하며 지원하지 않는 형식/비정상 숫자를 거절합니다.
- `audit`도 payload 검사값 안에 포함됩니다. SHA-256은 손상 검사용이지 인증용이 아닙니다. 새로운 Unity 캡처는 그때의 수동 상태를 저장하므로 원래 감사 지점 메타데이터를 이어 붙이지 않습니다.
- **감사의 내부 정책 메모리(이번 전투에서 과부하했는지, 이미 출격시킨 편대 목록)는 자동 재개하지 않습니다.** 불러온 이후는 사람의 명령입니다. 서로 다른 런타임에서 향후 전투 결과가 같다고 보장하지 않으며, 수동 A/B는 같은 Unity 빌드와 같은 캡처·고정 틱을 사용하십시오.

## 보존 픽스처와 다음 수동 검증

`Assets/_Project/Tests/EditMode/Fixtures/audit_v1/`에 실제 Mono 내보내기로 생성한 원본 두 개를 보존했습니다. 기존 v1/v2/v3 저장 픽스처와 과거 감사 JSON은 변경하지 않았습니다.

| 파일 | 실제 상태 | 용도 |
|---|---|---|
| `zephyr-17000-b1-t1.json` | 서풍·표준·첫 전투 0.1초, 출격/이동 명령 직후 | 진행 중 편대/선원 직렬화 회귀 |
| `zephyr-17000-b21-t100.json` | 6공역·41도약·21번째 전투 10초, 노병 순양함, 군수품 1, 선원 8명, 기관사 이동 중 | 누적 피해·구매·RNG·후반 수리 판단 재현 |

후반 픽스처에서 3번 편대는 감사의 항구 구매로 **강습 편대로 교체된 상태**입니다. 이 파일로 정찰 유지 효과를 비교하면 안 됩니다. 정찰/기관사/요격 A/B용으로는 같은 시드의 **7번째 전투 시작(`--snapshot-battle=7 --snapshot-tick=0`)**처럼 아직 정찰 편대를 보유한 시점을 내보낸 뒤 실제 자원·위협을 확인하십시오. `tick=100` 조사에서는 이 전투가 2공역 군집함, 군수품 1, 정찰 편대 보유 상태였음을 확인했습니다. 이것은 상태 조사이며 수동 전투 결과가 아닙니다.

다음 작업은 같은 캡처를 다시 불러오며 **기관사 함내 잔류 / 정찰 유지 / 요격 예약** 중 한 가지 운용만 바꿔 수리 도착 시간·추가 선체 피해·군수품·기체 손실을 기록하는 것입니다. 사람의 A/B, 전체 난이도/별도 시드 회귀, 서풍 수치 조정은 이번 작업에서 하지 않았습니다.

## 검증

- Unity **247 EditMode + 33 PlayMode = 280개 통과**. 신규 12개 상태/출처 검사와 1개 한·영 UI/격리 검사를 포함합니다.
- Python 통합 검사 **16개 통과**: 기존 감사 8개 + 지점 내보내기 8개. CLI 인자·경계 틱·부호 있는 시드·튜토리얼·미도달/종료/시간 제한·강제 적 출처·동일 payload·기존 파일 보존을 확인합니다.
- Mono → Unity 변환을 필드별 비교: 초기 픽스처 **869개**, 후반 픽스처 **918개** scalar 값 보존, float32 비트 일치. Unity의 null 문자열 → 빈 문자열 정규화만 허용합니다.
- 변경 전후 Standard/adaptive 첫 10시드 × 3기함 **30회**의 승패·시간·편대·자원 계측 전체 기록이 동일합니다. 전체 300회 감사를 다시 했다는 의미는 아닙니다.
- 런타임 컴파일 스모크와 프로젝트 정적 검증 통과. Windows 빌드/실행과 인간 완주율 검증은 남아 있습니다.
- **macOS 개발 빌드 성공**, 실제 실행에서 한국어 출처/빌드 경고, 10.0초 → F8 10.1초 → 동일 파일 재로드 10.0초 복원을 확인했습니다. 앱을 종료하고 같은 `/tmp` 캡처로 재시작해 영어 안내와 일시정지 상태도 확인했습니다. 키보드로 조작했으며 실제 마우스 입력은 별도 검증하지 않았습니다.
- 실행 전후 일반 `profile.json`·백업의 SHA-256이 동일하고, 없던 일반 `suspended_run.json`은 생성되지 않았습니다. 원본 픽스처와 가져온 캡처는 유지되며 저장된 테스트 상태도 6공역·시드 17000·10.0초·일시정지·원래 RNG임을 확인했습니다. 검수용 앱은 종료했습니다.

```sh
python3 -B tools/test_audit_checkpoints.py
python3 -B tools/test_wing_audit.py
```

필드 비교까지 재실행하려면 Unity EditMode 전체 테스트에 `AETHER_AUDIT_ROUNDTRIP_DIR=<새 임시 폴더>` 환경 변수를 지정한 후 다음을 실행합니다. 테스트는 기존 산출물을 덮어쓰지 않으므로 매번 새 폴더를 사용하십시오.

```sh
python3 -B tools/verify_checkpoint_roundtrip.py /path/to/fresh-roundtrip-output
```
